# 播放資料流

播放分成三層。下一層提出需求，上一層自行決定快取命中、下載、處理及預取；一次需求不代表一定要新增工作。

1. **下載**：`media-download.js` 負責來源傳輸、原生影片探測及整檔讀取。串流的 `cached-media-reader.js`、`http-stream.js`、`media-byte-cache.js` 負責位元組範圍、請求排程、快取、重試及網路預取。下載快取配額與省流量策略在這一層決定。
2. **媒體處理**：`media-session.js` 負責來源與編碼選擇、CENC 解密／轉封裝、ByteVC2 解碼及 H.264 轉碼、整檔備援，以及下一集預備與交接。`media-processor.js` 管理串流 Worker、WASM、預備片段及消費端 ACK；實際工作由 `cenc-remux-worker.js` 執行。
3. **播放**：`player.js` 負責操作介面、播放進度、切集與觀看紀錄；`cenc-remux.js` 是 MSE 呈現介面，負責追加片段、緩衝清除、時間軸與 seek 的呈現。`clear-key.js` 保留 MP4 索引探測與瀏覽器 EME/CDM 的相容路徑。

播放器透過 `media.request()` 要求可播放來源，透過 `media.updateContext()` 提供播放位置、暫停狀態及目前串流狀態。處理層自行決定是否準備下一集、只先下載，或開始產生片段。既有策略保留：接近片尾或目前處理已完成時可準備下一集；正在處理目前集數時，下一集的 CPU 工作等待交接。

MSE 消費片段後才回 ACK，形成背壓；下載層的位元組預取可獨立進行，不需要把整集解密或轉碼完。seek 命中 MSE 緩衝時由瀏覽器直接處理，未命中時向處理層要求該時間附近的片段，沿用原 Worker、WASM 與下載快取。

每個片源在下載層只有一個 response-body 讀取流程。必要讀取與讀取前方資料都由這個流程完成；第二層只提出位元組位置／長度並等待快取，不另開一個網路讀取工作排進 FIFO。下載層依快取缺口、目前連線位置和實測速度決定繼續讀或重新定位，不接收「seek」等播放器操作標籤；現有連線能在約一秒內到達缺口時，優先沿用。不同集的下載器、快取與重試額度各自獨立，可以同時下載；WASM 處理額度不會把跨集下載串行化。

只有實際等待 body 資料的時間才計入吞吐量，不把暫停或 ACK 背壓算成下載變慢。約八秒的主動讀取窗口內，速度持續低於該檔案平均位元組需求的 75% 時回報 `CENC_SOURCE_SLOW`，讓媒體處理層嘗試同畫質／編碼的其他官方候選。推測性讀取不使用必要讀取的重試額度。

下一集的串流建立與可播放狀態分別記錄為 `prefetch.prepared`、`prefetch.ready`。預載期間的慢速、讀取失敗或首次重試會觸發有界的候選輪替，候選耗盡後可重新查詢新的片源，受每步驟 20 次額度限制；刷新只得到已失敗 URL 時會提早停止。交接會保留已失敗 URL 與刷新額度，不把只有初始化標頭且已失敗的工作重新當成健康串流；正常交接沿用已取得的片段和下載快取。

單集工作與引擎的生命週期分開。完成工作的串流引擎最多保留一個、閒置 30 秒，可供後續相同種類的工作重用；重用前先等待上一集的讀取迴圈退出，並清除單集下載與輸出狀態。未完成、取消或失敗的工作終止 Worker，避免重用未確認清理完成的執行狀態。離開播放、停止與 pagehide 會清掉保留引擎。整檔 ByteVC2 備援仍使用獨立工作；一般 FFmpeg 備援沿用原本的共用引擎。

測試以 `createPlayer`、既有串流介面與瀏覽器可觀察的行為為準，不要求內部檔案切法或私有物件形狀。`player-behavior.test.mjs` 的相同行為案例已在重構前後執行。

## 匿名播放裝置與取源

瀏覽器以網站 origin 的 localStorage 保存一份匿名安裝資料（device_id、iid、cdid、clientudid、openudid、首次安裝時間）。識別不綁定代理 Worker 網址；重新整理、切集、切換 Worker 沿用同一份資料，不同瀏覽器使用者各自獨立。儲存不可用時僅保留本頁記憶體。Web Locks 可用時跨分頁合併初始化；否則只保證同頁合併。

裝置設定集中在 worker/vendor/device-profile.js：App 版本統一為已分析 APK Manifest 的 7.4.5.32／74532，註冊 payload、API query、API／註冊／媒體 UA 均共用版本、裝置型號、Android 版本及 DPI。SDK／簽名協定版本與硬體樣板保留既有適配器設定，未宣稱已從 APK 抓包驗證。

Worker 的 health 宣告 deviceSessions 與 deviceProfile。初次初始化使用 POST /api/device，已註冊識別隨 App 取源的 X-Playback-Device 標頭傳回，不放入 URL、來源快取或診斷 Log。Worker 冷啟動可直接沿用這份狀態，無須 KV。舊 Worker 未宣告能力時沿用原 API；舊客戶端沒有裝置標頭時則使用 isolate 內的相容快取。

註冊更新與每集取源分開：前景／背景到期時分別以 6／12 小時排程更新，版本 profile 改變也更新，但保留既有安裝識別並帶 did／iid。這些間隔不是 ID 有效期限；更新在背景執行，不阻塞正常取源；失敗繼續使用原識別。Worker 僅合併同一安裝的註冊，快取有數量上限，失敗冷卻也只影響該安裝。媒體 HTTP 200 空白只做有界的取源重試，不會更換裝置。

取源沒有固定間隔、全域佇列或跨請求拒絕狀態；一個慢速／403／429 請求不會擋住其他請求。單一 Worker 請求仍維持 deadline 與空白回應重試上限，不在同一次 Worker 請求內重試 403／429；跨請求恢復由前端分步驟執行。CDN 403 可換同畫質候選及重抓播放資訊，不能描述為整個播放一律停止；429 等待 Retry-After，未提供時預設等 8 秒，再有界重試同一候選，不重做成功的片源查詢。429 的策略是本專案的恢復選擇，APK 文件沒有確認其完整 runtime 策略。裝置重用參考 APK 的安裝識別生命週期；不代表已證明空白 200 的原因，也不能消除 Worker 共用出口 IP 的影響。

## 目前等待狀態

頁面小字只呈現目前前景等待，不串接先前取源錯誤。失敗／倒數重試保留錯誤摘要；開始新工作就改顯示當下工作。各層回報結構化事件，playback-status 將等待狀態記入 playback.wait（layer、phase）並更新文字：下載、解密／解碼、播放。

下載器僅在必要讀取未命中位元組快取時發出 media.wait（pending）；資料到齊、失敗、取消時解除。尚有必要讀取時優先顯示下載等待，讀取恢復後顯示媒體處理，MSE 追加後顯示等待畫面。正常播放時隱藏處理進度，waiting／stalled 再顯示目前阻塞處；背景預取只寫 prefetch.stage，不覆蓋前景訊息，交接時會補送仍在等待的必要讀取狀態。

Beta 提示進一步列出 POST /api/device 的初始化註冊、/api/source 的網頁及 App 畫質候選查詢、CDN 候選編號及探測、MP4 檔頭／定位 moov／moov 索引讀取，以及影片必要位元組下載。MP4 與影片下載會附 byte 範圍；本文等待的 receivedBytes 與標頭回應分開記錄。裝置更新若不阻塞播放，只記 device.lifecycle，避免假裝是前景的等待。

網頁／App 候選查詢次數以瀏覽器發出的 /api/source 請求計算；Worker 同輪最多 3 次空白回應重試仍在該請求內，UI 不冒稱能即時觀察這些內部子請求。

次數依 series／episode 與步驟分開，透過共享片源請求及預載 entry 保留；交接、候選輪替與刷新不重設。最多 20 次，從前景及預載的第一次嘗試開始合計；片源 API、CDN 探測、MP4 資訊讀取、影片下載與播放器載入不共用計數。失敗後採逐步增加、最多 8 秒的預設等待；Retry-After 可指定更久，介面會更新倒數。達額度上限後停止並提示稍後重新整理；重新整理保留裝置資料。錯誤 Range、不支援的格式，以及刷新仍沒有新候選可提早停止，不為湊滿 20 次重送無效 URL。

101 集提供的 Log 顯示片源 API 成功，失敗在 CDN 的 bytes 0–65535，曾於 8.745 秒收到 206，卻被涵蓋標頭與本文的 10 秒總限中止。metadata Range 現改為標頭及本文進展各有 10 秒閒置期限，整次另有 30 秒總上限；range.timeout 的 readPhase 會記 headers／body 和已收到的 bytes。這是修正逾時預算，不代表已驗證真實 CDN 恢復，也不證明風控原因。
